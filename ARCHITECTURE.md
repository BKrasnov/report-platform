# ARCHITECTURE — Report Platform (прототип)

## 1. Цель и рамки

Цель прототипа: показать, как команда может добавлять новые отчёты быстро и предсказуемо, с асинхронной генерацией, отслеживанием статусов и выдачей артефактов пользователю.

Что покрыто в текущем решении:
- Backend API для:
  - запуска отчёта;
  - получения статуса и списка запусков;
  - скачивания результата;
  - получения списка доступных отчётов и списка компаний.
- Асинхронная генерация через отдельный `worker`.
- Frontend (Web UI) для:
  - выбора отчёта и заполнения параметров;
  - запуска отчёта через API;
  - просмотра списка запусков и деталей (статус, прогресс, ошибка);
  - скачивания готового результата.
- Два разных отчёта:
  - `driver-medical-checks` (XLSX);
  - `company-summary` (PDF).
- Docker Compose для базы, API, worker и инициализации данных.

Это именно **прототип архитектурного подхода**, а не production-ready система.

## 2. Архитектура: компоненты, потоки данных, границы ответственности

### 2.1 Компоненты системы

1. `apps/api` (NestJS)
- Вход в систему для клиентов.
- Валидация входа и оркестрация use-case.
- Отдача метаданных отчётов/запусков и файлов.

2. `apps/api` worker (Nest application context в режиме фонового процесса)
- Периодически подбирает задачу из очереди запусков.
- Генерирует отчёт.
- Обновляет статус запуска.
- Выполняет watchdog для зависших `running` запусков.

3. `PostgreSQL`
- Хранит доменные данные (`companies`, `drivers`, `medical_checks`).
- Хранит очередь и состояние запусков (`report_runs`).

4. Файловое хранилище артефактов (`storage/reports/...`)
- Сохраняет сгенерированные файлы.
- API отдает файл пользователю по `runId`.

5. `apps/web` (React + MobX + mobx-view-model)
- Экран отчётов (запуск нового отчёта).
- Экран запусков (таблица статусов).
- Экран деталей запуска (статус, прогресс, скачивание).

6. `packages/shared`
- Контракты между фронтом и бэком: `reportId`, `status`, DTO/схемы (`zod`), публичные типы.

### 2.2 Границы ответственности по слоям

#### Backend
`api/controllers`
- Только HTTP-адаптеры и маппинг request/response.

`application/use-cases`
- Сценарии: создать запуск, список запусков, получить запуск, скачать артефакт, обработать следующий запуск, восстановить зависшие.

`application/services`
- Координация и инфраструктурные orchestration-сервисы (`ReportRegistryService`, `ReportRunnerService`, queue/storage service).

`domain`
- Сущности и доменные типы (`ReportDefinition`, `ReportArtifact` и т.д.).

`infrastructure`
- Репозитории (TypeORM), рендереры (XLSX/PDF), конкретные реализации отчётов.

#### Frontend - FSD подход, MVVM архитектура
`app`
- Инициализация приложения: роутинг, провайдеры, глобальный layout и общие стили.

`pages`
- Страничные сценарии и orchestration экранов (какие виджеты показать и как связать их VM).

`widgets` / `features`
- Переиспользуемые UI-блоки и пользовательские действия (запуск отчёта, обновление списка, скачивание артефакта).

`entities`
- Модель предметных сущностей на фронте: API-адаптеры и store для `report`, `report-run`, `company`.

`shared`
- Общая инфраструктура без бизнес-специфики: HTTP-клиент, базовые UI-компоненты, утилиты и базовые VM-хелперы.

#### Frontend: MVVM
`Model`
- Данные и доменные структуры UI-слоя: `entities/*` store + API-адаптеры и общие контракты из `packages/shared`.

`ViewModel`
- Состояние экрана/виджета и пользовательские сценарии: `pages/*/model/*VM.ts`, `widgets/*/model/*`.
- Инкапсулирует валидацию, вызовы API/store и преобразование данных в формат, удобный для View.

`View`
- React-компоненты из `ui`-слоёв (`pages/*/ui`, `widgets/*/ui`, `shared/ui`), которые только отображают состояние и вызывают действия VM.

Поток взаимодействия: `View -> ViewModel -> Model(API/store) -> ViewModel -> View`.

### 2.3 Потоки данных

#### Поток A: запуск отчёта
1. UI отправляет `POST /api/report-runs`.
2. API через `CreateReportRunUseCase`:
   - проверяет, что `reportId` зарегистрирован;
   - валидирует `params` через `paramsSchema` выбранного отчёта;
   - создает запись `report_runs` со статусом `queued`.
3. UI получает `runId` и переходит на страницу деталей/запусков.

#### Поток B: асинхронная генерация
1. Worker по таймеру запускает тик.
2. Worker восстанавливает stale `running` запуски (watchdog).
3. Worker атомарно забирает следующий `queued` запуск.
4. `ReportRunnerService` вызывает `generate(params)` у реализации отчёта.
5. Рендерер (`XlsxRendererService` или `PdfRendererService`) формирует файл.
6. `ReportArtifactStorageService` сохраняет файл.
7. Статус запуска обновляется в `succeeded` или `failed`.

#### Поток C: просмотр статуса и скачивание
1. UI запрашивает `GET /api/report-runs` и/или `GET /api/report-runs/:runId`.
2. После `succeeded` UI вызывает `GET /api/report-runs/:runId/download`.
3. API стримит файл из storage.

#### Поток D: каталог отчётов
1. UI запрашивает `GET /api/reports`.
2. API отдает список отчётов, собранный из registry.

## 3. Как добавить новый отчёт (инструкция для разработчика)

Ниже путь, по которому новый отчёт добавляется без изменения существующих отчётов.

### Шаг 1. Добавить контракт в `packages/shared`
1. Добавить новый `reportId` в `constants/report-ids`.
2. Добавить/обновить схему параметров отчёта (`zod`) в `schemas/*`.
3. Экспортировать типы/схемы через `packages/shared/src/index.ts`.

### Шаг 2. Реализовать backend-отчёт
1. Создать папку `apps/api/src/features/report-platform/infrastructure/definitions/<new-report>/`.
2. Добавить класс `*Report`, реализующий `ReportDefinition<TParams>`:
   - `id`, `title`, `description`, `format`, `paramsSchema`;
   - `generate(params): Promise<ReportArtifact>`.
3. Внедрить нужные репозитории/сервисы в конструктор отчёта.
4. Если нужен новый формат:
   - добавить новый рендерер в `infrastructure/renderers`;
   - подключить его в `reports-core.module.ts`.

### Шаг 3. Зарегистрировать отчёт в registry
1. Подключить новый класс в `modules/reports/reports-core.module.ts`.
2. Добавить его в провайдер `REPORT_DEFINITIONS`.

После этого:
- отчёт автоматически появляется в `GET /api/reports`;
- `POST /api/report-runs` начинает принимать его `reportId` и `params`.

### Шаг 4. Подключить в UI
1. Добавить отображение нового шаблона в `apps/web` (select/карточка отчётов).
2. При необходимости добавить поля формы под его параметры.
3. Использовать уже существующий сценарий запуска (он общий для всех отчётов).

### Шаг 5. Проверить
1. Unit-тесты контракта/валидации.
2. Unit-тест `generate()` нового отчёта.
3. E2E smoke: создать запуск → дождаться `succeeded` → скачать артефакт.

## 4. Принятые решения и альтернативы

### Решение 1: Асинхронность через БД-очередь (`report_runs`) + отдельный worker
Выбрано:
- минимальная инфраструктура для прототипа (без Redis/RabbitMQ);
- понятная транзакционная модель;
- легко поднять в `docker-compose`.

Альтернативы:
- Redis/BullMQ;
- RabbitMQ;
- SQS/Kafka.

Почему не они сейчас:
- выше операционная и интеграционная сложность для MVP.

### Решение 2: Реестр отчётов (`REPORT_DEFINITIONS` + `ReportRegistryService`)
Выбрано:
- единая точка подключения новых отчётов;
- API получает список отчётов из того же источника, что и worker.

Альтернативы:
- hardcoded switch-case;
- динамический автоскан файлов/плагинная загрузка.

Почему текущее:
- явная регистрация проще ревьюить и безопаснее для команды на этапе прототипа.

### Решение 3: Frontend на FSD-слоях (`app/pages/widgets/features/entities/shared`)
Выбрано:
- явные границы ответственности между частями UI;
- предсказуемая структура при росте числа экранов и фич.

Альтернативы:
- слоистая (layered) frontend-архитектура;
- FEOD (Fractal Entity Oriental Design) — более гибкий вариант FSD с модульно-фрактальной структурой и локальными границами модулей вместо жёсткой глобальной иерархии слоёв.

Почему текущее:
- для текущего MVP FSD проще стандартизировать в команде: понятные правила импорта и размещения кода, меньше архитектурной неоднозначности.

### Решение 4: Frontend на MVVM (View + ViewModel + Model)
Выбрано:
- разделение представления и бизнес-логики UI;
- перенос сценарной логики экранов/виджетов в отдельные VM.

Альтернативы:
- Flux с Redux Toolkit;
- React Query + провайдеры на `useContext`/`useSyncExternalStore`.

Почему текущее:
- при росте бизнес-логики компоненты остаются «тонкими», а состояние и сценарии становятся проще для тестирования и повторного использования.

### Решение 5: Frontend на `mobx-view-model` + отдельные VM для страниц/виджетов
Выбрано:
- чёткое разделение UI и состояния;
- поддержка lookup между VM через общий store (для сценариев cross-widget взаимодействия).

Альтернативы:
- Flux с Redux Toolkit.
- React Query + провайдеры на `useContext` или `useSyncExternalStore`.

Почему текущее:
- для high-load проектов с большим объёмом бизнес-логики снижаем нагрузку на компоненты, делая их «тонкими» и вынося логику в VM.

Почему именно `mobx-view-model`:
- Библиотека используется как полноценный архитектурный слой MVVM для React + MobX.
- Ключевая причина выбора — не только инкапсуляция логики в VM, но и инфраструктура взаимодействия между несколькими VM:
  - общий `ViewModelsProvider`;
  - lookup по store (`get`, `getAll`, `useViewModel`);
- Это позволяет строить связные сценарии между страницей и вложенными виджетами без проп-дриллинга и без искусственных глобальных сторов.

Минусы:
- Есть дополнительный runtime-слой (`withViewModel`, observer-обёртки, контексты, собственный lifecycle VM), из-за чего дерево React-компонентов становится больше.

Почему это подходит именно здесь:
- В проекте уже есть несколько экранов и виджетов с пересекающимися сценариями (запуск, обновление, детализация, скачивание).
- Нам важно иметь расширяемую модель взаимодействия между частями UI при росте числа отчётов и форматов.

## 5. Что не сделали и почему. Что добавили бы для продакшена

### Не сделали в прототипе
1. Полноценную внешнюю очередь сообщений через RabbitMQ (скорее всего).
- Почему: для MVP достаточно БД-очереди, дешевле.

2. Объектное хранилище (S3/MinIO) и signed URL.
- Почему: локальный volume проще для демонстрации.

3. Push-обновления статусов через WebSocket.
- Почему: для прототипа подойдет polling через HTTP API; реализация и поддержка real-time канала увеличивают сложность.

4. Полноценный контракт API через Swagger/OpenAPI.
- Почему: в MVP важнее был рабочий контур генерации отчётов; детальная контрактная документация и стандартизация схем вынесены в следующий этап.

### Что добавил бы для продакшена
1. Внешняя очередь + гарантии доставки/повторов.
2. S3-совместимое storage + lifecycle policy на артефакты.
3. WebSocket-канал для real-time обновлений статусов запусков и прогресса генерации.
4. Полное Swagger/OpenAPI-описание (включая примеры, схемы ошибок и версионирование API).

## 6. Кратко о соответствии тестовому заданию

Требования задания покрыты:
- асинхронная генерация отчётов;
- API для списка отчётов, запусков, статусов, скачивания;
- Web UI для запуска и мониторинга;
- два разных отчёта и паттерн масштабирования;
- инфраструктура запуска через docker-compose для backend-контура.

Ключевая идея решения: **думать широко (расширяемость и границы), реализовать узко (рабочий MVP с понятным путём роста).**
